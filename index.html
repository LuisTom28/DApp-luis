01FUNDAMENTOS DE SOFTWARE

01 · EL CONCEPTO

¿Qué es una arquitectura desacoplada?

Es una forma de diseñar una aplicación como un conjunto de servicios pequeños e independientes. Cada uno se encarga de una función concreta y se comunica con los demás mediante interfaces bien definidas, normalmente una API.

🏙️

UNA ANALOGÍA COTIDIANA

Piensa en una ciudad

En una ciudad, el hospital, el mercado y el transporte cumplen funciones distintas. Si una tienda cierra, la ciudad no deja de funcionar por completo. En una arquitectura de microservicios, cada servicio es como uno de esos lugares: especializado y conectado con los demás, pero capaz de evolucionar por su cuenta.

✦ Idea clave: desacoplar no significa que los servicios no se comuniquen; significa que colaboran sin depender demasiado de los detalles internos de los otros.

02 · DOS ENFOQUES

Monolito vs. microservicios

No existe una solución perfecta para todos los proyectos. La elección depende del tamaño, las necesidades y la capacidad del equipo.

Comparación entre una arquitectura monolítica y una arquitectura de microservicios
Aspecto▰ Monolito⠿ Microservicios
DespliegueLa aplicación se publica como una sola unidad.Se puede desplegar cada servicio de forma independiente.
EscalabilidadSe escala toda la aplicación, incluso si solo una parte lo necesita.Se escala el servicio que requiere más recursos.
FallosUn problema puede afectar a toda la aplicación.Un fallo puede limitarse a un servicio si el sistema está bien diseñado.
EquiposLos equipos suelen trabajar sobre una base de código compartida.Equipos pequeños pueden responsabilizarse de servicios distintos.
ComplejidadMás sencillo de iniciar, probar y operar en proyectos pequeños.Mayor complejidad de red, observabilidad y coordinación operativa.

ⓘ Un monolito bien organizado puede ser una excelente opción; dividir una aplicación demasiado pronto también añade trabajo.

03 · LAS PIEZAS

Componentes clave

Estas son algunas piezas frecuentes en un sistema distribuido. No todas son obligatorias en cada proyecto.

API Gateway

Es una puerta de entrada que recibe las solicitudes de los clientes y las dirige al servicio adecuado. También puede gestionar autenticación y límites de uso.

Comunicación entre servicios

REST permite intercambiar solicitudes y respuestas. La mensajería facilita una comunicación asíncrona: un servicio publica un evento y otro lo procesa después.

Datos por servicio

Cada servicio es responsable de sus propios datos. Esto reduce dependencias entre equipos, aunque hace más complejo coordinar información compartida.

Contenedores

Herramientas como Docker empaquetan un servicio con sus dependencias para que se comporte de forma consistente en distintos entornos.

Orquestación

Plataformas como Kubernetes ayudan a desplegar, escalar y recuperar contenedores cuando una instancia deja de responder.

Y una base importante

Monitoreo, registros y trazas ayudan a entender qué ocurre cuando una solicitud pasa por varios servicios.

04 · UNA DECISIÓN INFORMADA

Ventajas y desafíos

Separar una aplicación puede dar flexibilidad, pero también exige buenas prácticas y una operación cuidadosa.

↗

Ventajas

  • ✓
    Escalado selectivo

    Aumenta la capacidad solo donde hay más demanda.

  • ✓
    Despliegues independientes

    Actualiza un servicio sin publicar toda la aplicación.

  • ✓
    Autonomía de equipos

    Equipos pequeños pueden trabajar y entregar cambios con más independencia.

  • ✓
    Aislamiento de fallos

    Con mecanismos de resiliencia, algunos problemas quedan contenidos.

⚙

Desafíos

  • !
    Más piezas que operar

    Hay que desplegar, configurar y mantener más componentes.

  • !
    Fallos de red

    La comunicación remota puede fallar o demorarse; conviene diseñar reintentos y tiempos límite.

  • !
    Datos distribuidos

    Una operación que cruza servicios puede requerir coordinación eventual.

  • !
    Diagnóstico más exigente

    Se necesitan registros, métricas y trazas para seguir una solicitud completa.
